# 坑记录

从这里开始记录，每条写现象、根因、改法。

## 覆盖更新中断后重试删除唯一旧版备份

**现象**：安装目录已改名为 `.s2arm-old`、新版还没改名到安装位置时中断，再次执行 `apply()` 会删除旧版备份，随后因安装目录不存在而失败。

**根因**：更新入口无条件清掉已有备份，再调用要求安装目录存在的 `swap()`，没有恢复两次改名之间的中断状态。

**实验数据（期望 → 真结果）**：Mac arm64、Python 3.15.2、基线 `8771609`；用合成目录构造第一次改名后的落盘状态。重试成功安装新版 → 改前失败且旧版消失、改后成功；新版暂存目录丢失时保留并重启旧版 → 改前旧版消失、改后恢复旧版；恢复改名被拒时原备份保留 → 改前消失、改后保留。`ApplyTests`、`RunnerTests`、`Ed25519Tests`、`VersionTests` 共 15 项通过。临时副本换回基线 `updater.py` 后，两项点名回归重新失败。

**做法**：安装目录缺失而旧版备份存在时先恢复旧版，再走正常替换。未执行真实安装包更新、断电或 Windows 文件占用验收；该验证仅覆盖两次改名之间的中断状态。

## 清理中间产物时沿链接删除存档目标

**现象**：`iPhone/<程序号>/intermediate` 是指向同库 `saves/<程序号>` 的目录链接时，`prune_build()` 删除存档目标，链接本身却留下。

**根因**：`library._rm()` 先经 `contained()` 解析链接，再检查 `is_symlink()`；目标仍在游戏库内就通过了包含检查。父目录是链接时也会删除它指向的文件。

**实验数据（期望 → 真结果）**：Mac arm64、Python 3.15.2、基线 `8771609`，均为临时目录与合成字节。自动清理后存档保留 → 改前文件消失、改后内容原样保留；显式清理、库外目标、文件链接和悬空链接同测。`test_cleanup_links`、`test_free_space`、`test_saves` 共 63 项：62 项通过、1 项 Windows junction 用例因宿主不符跳过。临时副本换回基线 `library.py` 后，两项点名回归重新失败。

**做法**：先核对未解析的路径是否属于清理根，拒绝经过父目录链接；叶子链接只删除链接本身，Windows junction 使用 `rmdir`。未做 Windows 真机验证，也不据此宣称能消除并发路径替换的所有竞态。

## 发版 Mac App 出包失败：shader_extract_failed（issue #8）

**现象**：  
发版 Mac App（如 v0.1.0），游戏 RomFS 要解码器（Oodle LZ5）或运行时 GLSLC 时，出包报 `shader_extract_failed`，阶段停在「分析画面」。

**根因**：  
- `pack/stage_extract.sh:63` 调 `tools/host_build.sh` 现场 make 编 Mac 宿主（含 C#，S2A_CS=1）
- 发版 App 只带 Runtime（`pack/jobs/core.py:500` 设 `DOTNET_ROOT=Runtime/dotnet`），无 SDK
- make 的某步调 `dotnet --version`，Runtime-only dotnet 报「No .NET SDKs were found」退非 0
- 失败被 `stage_extract.sh:63` 归因：「【红】t<游戏 ID> 编译 Mac 宿主失败（The command could not be loaded...）」
- 上层按阶段 `sh_extract` 映射错误码 `shader_extract_failed`

**实验数据**：  
- 设备：Mac（发版 App v0.1.0，S2ABuildID=7aff9afa-86be9c95）
- 数据目录：<本机复现用的临时数据目录>
- 游戏：010021C000B6A000 以撒重生+ v1.7（中文忏悔本，含 Oodle LZ5 → decoder_need 为真 → S2A_CS=1）
- 期望：ipa completed
- 真结果：rc=1，analyze 2/10（26 秒），错误码 `shader_extract_failed`
- 日志证据：
  - `Runtime/dotnet/dotnet --version` 输出「No .NET SDKs were found」
  - `refresh.log` 第 8 行「【红】t010021c000b6a000 编译 Mac 宿主失败（The command could not be loaded...）」
- 负对照：暗黑3（不需解码器）未复现，task completed 346 秒

**做法**（提交 45d5ffe，分支 fix/packaged-mac-host）：  
1. **打包时已放宿主**：`launchers/macos/bundle_engine.py:179` 已有 `shutil.copytree(host, destination / "Binaries/S2ArmGame.app")`，打包时把编好的宿主（S2A_CS=1，含 C#）放进引擎 Binaries/ 目录
2. **检测并设环境变量**：`pack/jobs/core.py` 的 `Context.env` 方法，在发版环境（runtimeSchema 3/4）中：
   ```python
   from embedded import artifact
   try:
       bundled_host = artifact(self, "S2ArmGame.app")
       if bundled_host and (bundled_host / "Contents/MacOS/s2arm-host").is_file() and (bundled_host / "Contents/MacOS/libs2a_vaguard.dylib").is_file():
           env["S2A_BUNDLED_HOST"] = str(bundled_host / "Contents/MacOS/s2arm-host")
           env["DM_GLSLC_HOST"] = str(bundled_host / "Contents/MacOS/s2arm-host")
   except Exception:
       pass   # 源码树开发：没有内置宿主
   ```
3. **跳过现场编译**：`pack/stage_extract.sh:51-64` 在需要宿主时，检测 `S2A_BUNDLED_HOST`：
   - 如果设置且文件存在 → 输出「[s2a] 使用发版 App 内置 Mac 宿主：$S2A_BUNDLED_HOST」，跳过 `host_build.sh`
   - 否则 → 按原逻辑现场编译（源码树开发构建）
4. **单测覆盖**：`tests/stage_extract_test.sh` 添加用例「有内置宿主 → 不编宿主、跳过 host_build」

**射程**：  
- ✅ 所有发版 Mac App，游戏需要解码器（Oodle LZ5）或运行时 GLSLC
- ✅ 调用链：oneclick → refresh → stage_extract → extract.sh / glslc_offline.py（DM_GLSLC_HOST 环境变量传递）
- ✅ 源码树开发构建不变（runtimeSchema != 3/4 或 artifact 返回 None 时走原路径）
- ✅ Windows 不受影响（pack/orch/oneclick_win.py，不走 Mac stage_extract）
- ⚠️ 边界：如果打包流程被修改，未把宿主放进 Binaries/，会退回现场编译（因 artifact 返回 None，与源码树开发相同）

**验证**：  
- 单测：`bash tests/stage_extract_test.sh` 全通（23 个 Python unittest + 40+ 个 shell 断言）
- 现有 App：`/Applications/S2Arm.app/Contents/Resources/Engine/Binaries/S2ArmGame.app/` 存在，包含 s2arm-host (106M，含 C#) 和 libs2a_vaguard.dylib (67K)
- 完整打包 + 游戏测试未执行（耗时 15-30 分钟，当前负载 10+）

## 命令行出完包，Mac 前端认不到（装机 / 推资源包报 container_stale）

**现象**：用 `pack/oneclick/oneclick.sh` 命令行出好的 IPA 与资源包都在 `<游戏库>/iPhone/<程序号>/` 下，Mac 前端却说这款没有 iPhone 版；点「装到 iPhone」或推资源包报 `container_stale`。

**根因**：启动器判「这款的产物是不是按本壳出的」看 `<输出>/shell.id`（`pack/jobs/ipa.py` 的 `SHELL_STAMP`，`ipa.current_root()` 只有它对得上当前壳编号才认这份产物）。这份戳只有**启动器自己的打包任务**会写，命令行一键出包（`oneclick.sh` → `ipa.sh` → `ipa_tail.py`）不写，于是产物齐全但前端判「没出过」。

**改法**：`ipa.sh` 出包成功时把壳编号（`<壳目录>/manifest.json` 的 `details.shellId`）写进产物根 `.shell_id` 并随 `root_commit` 提交；`oneclick.sh` 出包成功后把它转交成 `<输出>/shell.id`（与启动器写同一份、同一口径）。

**读数**（期望 → 真结果）：命令行重出这款后 `<输出>/shell.id` → 期望 `e2c369640047cade`，真结果 `e2c369640047cade`；用引擎自己的 `install.latest_ipa()` / `ipa.current_root()` 复核 → 期望返回 IPA 与现行产物根，真结果都返回了（改前 `current_root` 返回 None）。
## 出包停在「出包 2/5」、错误码只有 package_failed「原因没认出来」

**现象**：iPhone 出包到 `出包 2/5` 后工具退出，错误摘要写「Packaging incomplete / We couldn't recognize the cause」（9.78 GB 的 PERSONA4 The GOLDEN，0.1.0，iOS 目标 iPhone 17 Pro）。`pack/ipa.sh` 的 `PN=5` 是 ①组装 ②签名 ③打 ipa ④资源包 ⑤资源包核对；进度只到 2，说明停在 ③「打 ipa」（`pack/ipa_tail.py` 的 `write_ipa` 步）——其余步要么有自己的日志（build.log / sign.log / pack.log / verify.log），要么在 `pack/jobs/ipa.py` 的 `PACKAGE_FAILURE_PREFIXES` 里能映射。

**根因**：③ 这一步有两处把原因丢掉。一是 `ipa_tail.assemble` 调 `step()` 时没给日志，输出落进 `$W/pkg/tail.out`，而 `ipa.sh` 失败时只把 `build.log` 拷进 `S2A_ROOTS/.failed/`、随后 `root_abort` 删掉整个临时产物根，于是真正的原因（体积账 / errno / zipfile 异常）既没进红行也没进摘要；`PACKAGE_FAILURE_PREFIXES` 也没有「打 ipa」这一项，归因只能落到 `package_failed`。二是同一类「原因看不见」的口子：`app_bundle.write_ipa` 按设计不写 zip64（侧载工具读不了），而 32 位上限只有「单文件」一道闸，条目数 / 整份字节超了由 `zipfile` 在写条目或收尾时抛 `LargeZipFile`；它不是 `OSError`，`main()` 的 `except (OSError, ValueError, RuntimeError)` 也接不住，于是变成裸 traceback，父进程只拿到退出码。**这单具体是撞了哪条上限、还是别的 errno，以修复后红行里的原文为准**（IPA 不一定到 2 GiB，先不认定）。

**改法**：③ 有独立日志 `pkg/archive.log`，失败时把最后一行（红行优先）写进红行与错误摘要，`ipa.sh` 失败时也把这份日志留到 `S2A_ROOTS/.failed/`；`write_ipa` 归档前先算体积账（条目数 / 单文件上限能提前判死，整份取决于压缩后大小），收尾的 `LargeZipFile` 转成带体积账的 `BundleError`，`main()` 再兜一层，任何一条路都不落裸 traceback。

**读数**（期望 → 真结果）：归因 `打 ipa 失败（OSError: [Errno 28] No space left on device）` → 期望 `disk_full`，改前 `package_failed`、改后 `disk_full`（`pack/jobs/errors.classify_failure`，合成输入）；`tests/app_bundle_test.py` 新增三条体积账用例 → 改前 2 条 ERROR、改后全绿（34 条，skip 2）；`tests/ipa_tail_test.py` 新增 `archive_reason` 用例 → 改前 AttributeError、改后全绿（7 条）。

## Windows 玩家出 CRI 压缩的游戏：抽取报 WinError 2（issue #95）

**现象**：PERSONA4 The GOLDEN，v0.1.3，Windows 11，「抽取 + 直连库」阶段失败，`direct_lib.log` 只有 `concurrent/futures/_base.py line 401` 和 `FileNotFoundError: [WinError 2]`，后面不带路径。

**根因**：`nxsh_extract._cri_lib` 遇到 CRILAYLA 数据时在子进程池里现场调 `clang` 编 `crilayla.c`。Windows 发版预编了 dsx 和 Yaz0 小库，漏了这一个；玩家机器没有 clang。构建机装了 LLVM，所以 11-05、11-06 的女神异闻录5 都没暴露。Windows 上起子进程失败的 `WinError 2` 不带文件名，打开文件失败是 `Errno 2`，可以据此区分。

**改法**：`bundle_prepare_win.py` 把库编进 `Binaries/Prepare/codecs`，文件名带源码摘要；`_cri_lib` 先用预编件；`oneclick_win --check` 缺这份预编件时起单前就报红。

**读数**（期望 → 真结果，Windows 11，PATH 去掉 clang，真实入口 `nxsh_extract.py`，手造含 CRILAYLA 的 CPK，1 支着色器）：旧代码 → 期望 WinError 2，真结果 rc=1、同样的 `_base.py line 401` + `WinError 2`；新代码无预编件 → 期望 WinError 2，真结果相同；新代码有预编件 → 期望键 `503475149b866d8c`，真结果 rc=0、解开 CRILAYLA 1 段、键相同。
## Windows：机器设了 LANG=C / en_US，中文路径被 cygpath 截断（issue #85）

**现象**：Windows 出包在「抽取 + 直连库」1 秒内失败。安装在中文目录时报 `can't open file 'D:\translator\spvc_inproc.py'`（摘要里是 `D:[PRIVATE_PATH len=26 depth=2]`），装到英文目录后报 `D:/ 缺 romfs/ 或 exefs/main`。

**根因**：`direct_lib.sh` 用 `cygpath -m` 转路径。MSYS 的 `cygpath` 在 `LANG` / `LC_ALL` 为非 UTF-8 值时，输出在第一个非 ASCII 字符处截断；作业环境继承了机器上的语言变量。脱敏器统计 `len` 时不含盘符，且把双反斜杠算一个，看长度要按这个口径算。

**改法**：`win_runtime_env` 和 `s2arm_env.cmd` 设 `LC_ALL=C.UTF-8`，所有 Windows 出包作业生效。

**读数**（期望 → 真结果，Windows 11，Git Bash `cygpath`，真实 `direct_lib.sh`，产物根在 `游戏库` 下）：`LANG=C`、`LANG=en_US`、`LC_ALL=C`、`LC_ALL=POSIX` 下 `cygpath -m` → 期望截断，真结果 `C:/Users/example/v85/`；`LANG=C` 跑旧环境 → 期望与玩家同形，真结果 `C:/Users/example/v85/ 缺 romfs/ 或 exefs/main`；`LANG=C` 和 `LC_ALL=C` 跑新环境 → 期望过这一检查，真结果过了第 61 行（后面失败是精简目录缺 `tools/progress.sh`）。

## Windows：任务记录原子替换撞上读方，长任务整局失败（issue #130）

**现象**：Windows 长任务报 `journal_write_failed`（拒绝访问），事件日志写入正常，磁盘和权限都没问题。

**根因**：`atomic()` 用 `os.replace` 替换任务记录。Windows 上目标文件被打开且没带 `FILE_SHARE_DELETE` 时，替换抛 `PermissionError`；Python 的 `open()` 不带这个共享标志，一次撞上就让整局失败。

**改法**：Windows 上 `PermissionError` 退避重试 6 次（共约 1.6 秒），其余平台不重试。

**读数**（期望 → 真结果，Windows 11，Python 打开目标文件 0.3 秒）：旧 `atomic()` → 期望 `PermissionError`，真结果 `[WinError 5] 拒绝访问`；新 `atomic()` → 期望写入成功，真结果成功，用时 0.38 秒。

## RomFS 里的 macOS 垃圾进了索引，游戏枚举到后读不到而闪退

**现象**：iPhone 上《火焰纹章 万缕千丝》播片后必闪退，日志是 `svc 0x21` 抛 `FileNotFoundException`，文件是 `romfs/Movie/.DS_Store`，服务异常回成 2010-0221 后游戏 Break 退出。

**根因**：`pack/pack.py` 打资源包时跳过 `.DS_Store` 和 `._*`，但 `romfs_list.py` 的盘点和 `RomFsIndex` 的枚举不跳过，索引里有、手机上没有。

**改法**：`romfs_list.scan`、`RomFsIndex.Write`、`OverlayFiles`、`RomFsFromDirectory` 按同一规则过滤。只滤这两类，游戏自己的点开头文件保留。文件清单变了，索引会重出，老包要重新出包才生效。

**读数**（期望 → 真结果，手造 romfs 含 `.DS_Store`、`Movie/._a.mp4`、`.build.config`）：修前 C# 单测 → 期望红，真结果 7 项红；修后 → 期望全绿，真结果 `.DS_Store` 和 `._*` 不在镜像、`.build.config` 在。

## Windows：长路径前缀漏给调用方，出包报 is not in the subpath（issue #138）

**现象**：Windows 出包在「八个轻阶段」失败，报 `'…' is not in the subpath of 'C:…'`，只有路径达到 240 字符的目录才触发。

**根因**：`winlong` 给 `os.scandir` 的路径加了 `\\?\` 前缀，`DirEntry.path` 跟着带上前缀，`roots.plain_entries` 拿它和不带前缀的根目录做 `relative_to`，比不上。

**改法**：`scandir` 只在系统调用里用前缀，返回给调用方的路径保持调用方的写法。

**读数**（期望 → 真结果，Windows 11，根目录 224 字符，文件 258 字符）：旧实现 `romfs_list.scan` 后 `relative_to` → 期望 `ValueError`，真结果 `ValueError`（路径带 `\\?\`）；新实现 → 期望 `systemdata/nintendo/fonts/a.bfttf`，真结果相同。

## 改写器把代码段里的内嵌数据当指令扫（issue #108）

**现象**：Spelunky 2 改写失败，`need=1602257 gaps=411557`，缺口里 310461 条是 hvc / smc / dcps，每 MB 约 1000 条且均匀分布，另有 19983 条读写 x18。

**根因**：`scan()` 对整个代码段线性解码。这款约 338 MB 的代码段里混有大量数据，数据碰巧解码成这些指令。

**改法**：`data_in_text` 在有足够证据时用函数范围、动态符号和直接分支闭包算真实代码，范围外不改写、不算缺口；证据不足或范围不可信时不启用。

**读数**（期望 → 真结果）：合成模块（含 288 MB 代码段）→ 期望数据区缺口全部排除、数据字节不变、函数内和分支可达的 svc 仍改写，真结果全部相符；代码段最大的 6 款旧 / 新改写器 → 期望全部产物逐字节相同，真结果差异 0。Spelunky 2 原件不在手上，要玩家重新出包确认。

## Windows 深路径下子进程永远起不来，出包卡在播种

**现象**：数据目录根 202 字符通过，222 字符卡死。父进程停在 `subprocess` 的 `CreateProcess`，CPU 持续上涨；子进程处于挂起状态，0 个模块。

**根因**：`work_temp` 把 `TMP` / `TEMP` 指到工作目录下，路径超过 `MAX_PATH` 后，`CreateProcessInternalW → BasepQueryAppCompat → GetTempPathW` 在这段兼容性查询里循环不退出（原生栈抓到的）。

**改法**：路径超过 200 字符时，临时目录改到同盘根下的 `S2ArmTmp\<摘要>`，结束时删除；盘根建不了就退回系统 Temp。

**读数**（期望 → 真结果，Windows 11，数据目录根 224 字符，真实 S2Arm.exe 启动）：修前 → 期望卡在播种，真结果子进程 0 模块、播种日志 0 字节；修后 → 期望过播种，真结果 `seed.log` 87 字节、进入「八个轻阶段」。
## 单壳容器打开游戏库时主线程逐文件核对资源包

**现象**：玩家反馈每次打开 App 都要等很久才能操作。

**根因**：游戏库建好和每次回前台都调 `s2a_import_state`，按 `index.tsv` 对每个文件 `stat`，在主线程上。日志里「进程创建到键盘扩展」的 14–24 秒不能当等待时间：进程可能是 iOS 预热的（日志有「预热 → 场景激活 +9551 ms」），键盘扩展要到第一次交互才加载。

**改法**：库界面用快判，`.applied` 等于清单的 `index_sha256` 就算就绪；完整核对留在点 Play 后的导入闸门。新增打点「[起局] 游戏库界面可操作」。

**读数**（期望 → 真结果，iPhone 17 Pro Max，动森 10.5 万文件，热缓存，各 3 次）：host.log 重建到库界面 → 修前 2.46–2.51 秒；修后打点 → 进程创建到可操作 127.5–212.6 ms。冷缓存没有复现条件。

## Windows 深路径：工作区走短入口

**现象**：数据目录很深时，原生工具、bash、临时目录都可能踩 `MAX_PATH`。

**做法**：任务开始在 `%LOCALAPPDATA%\S2A\j\<4 位短号>` 建 0 字节目录联接，指向玩家选的目录，之后全部走短路径，TEMP 和产物仍落在玩家目录；任务结束拆除，只删联接本身。`os.path.realpath` / `Path.resolve` 会把联接展开成长路径，`winlong` 统一映射回短路径，否则和短路径比 `relative_to` 失败。给玩家看的文字用 `shortroot.show` 换回玩家路径。

**坑**：`_winapi.CreateJunction` 的目标不能加 `\\?\`，它自己拼 `\??\`，再加一层是非法联接，访问时报 WinError 123。判卷（ReFS 克隆）要用真实路径，入口在系统盘、目标可能在别的盘。

**读数**（期望 → 真结果，Windows 11，真实 S2Arm.exe，数据目录根 224 字符，Human: Fall Flat）：整款出包 → 期望成功，真结果 93 秒，ipa 48 MB，日志只显示玩家路径；结束后入口目录 → 期望空，真结果空。
